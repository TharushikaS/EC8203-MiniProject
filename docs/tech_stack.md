# Technology stack and justification

Each choice below is tied to a constraint of the Smart Grid use case, not to general popularity.

| Layer | Technology | Why this, for this use case | Alternatives considered |
|---|---|---|---|
| Streaming ingestion | **Apache Kafka 3.8 (KRaft)**, topic `meter-readings`, 6 partitions, key = `household_id` | Meters are many independent producers, and readings must be **ordered per meter**. Keying by household gives per-meter ordering while spreading load over partitions for parallel consumers. The durable log decouples the meters from the processors, so a Spark restart loses nothing, and its **7-day retention gives the speed layer a replay window**. `acks=all` + idempotent producer means no loss and no broker-side duplicates. The separate `meter-readings-dlq` and `grid-alerts` topics make rejected data and alerts consumable by other systems. KRaft mode removes ZooKeeper, which means fewer containers on a laptop. | RabbitMQ (no replayable log, weak ordering at scale); MQTT (a good *edge* protocol for meters, but in production it would bridge into Kafka rather than replace it). |
| Batch-source ingestion | **File drop + Airflow sensor** (CSV tariffs, JSON weather) | Utility billing systems publish **end-of-day extracts as files**. A sensor models this honestly: late files, missing files and re-issued versions (`.v2.csv`). Atomic rename prevents half-read files. | Pushing tariffs through Kafka: over-engineering for one file a day, and it loses the "file version = correction" semantics. |
| Stream processing | **Spark 3.5 Structured Streaming** | We need **event-time windows with watermarks** (meters report late), **streaming deduplication** (`dropDuplicatesWithinWatermark`) for retried sends, stateful aggregation with a **RocksDB state store**, and **exactly-once-style sinks** (checkpointed offsets + idempotent `foreachBatch` upserts). Using the same engine as the batch layer lets us **share transformation code** (`speed/transforms.py`), which removes Lambda's biggest weakness: logic duplicated across two code bases. | Apache Storm (tuple-at-a-time, no built-in event-time windows or watermarks, would need a separate batch engine and code base); Flink (excellent streaming, but a second engine for the batch side). |
| Batch processing | **Spark 3.5 (PySpark) batch job** | A full recompute per day from the Parquet master dataset: exact dedup across the whole day, a broadcast join with the tariff table, and pricing through `mapInPandas`, so the **same Python billing function** runs distributed. It scales horizontally when households grow from 250 to millions. | Pandas only (cannot scale past one machine's memory); SQL in Postgres (would turn the serving DB into the compute engine). |
| Orchestration | **Apache Airflow 2.10** | The batch layer is a **dependency chain triggered by data availability** (sensor → validate → Spark → reconcile → report → metrics). Airflow gives retries, failure callbacks (feeding our alerting), run history, and a UI showing each simulated day's run. Parameterised manual DAGs (`smartgrid_recompute`) give an **auditable recompute / backfill** mechanism. | Cron (no dependencies, retries or visibility); Dagster / Prefect (fine choices, but Airflow is the module's specified orchestrator and the industry standard). |
| Master dataset | **Parquet on a shared volume**, partitioned by `event_date` | Immutable, append-only, columnar and compressed, which is ideal for a batch layer that reads one day's columns at a time. Partition pruning makes a single-day recompute cheap. The streaming file sink's `_spark_metadata` log means the batch reader only sees committed files. Standing in for HDFS/S3 (the same code works on `s3a://`). | Keeping history in Kafka (retention-bound, costly per GB, poor for analytics); Postgres (row store, and would mix OLTP serving with OLAP history). |
| Serving store | **PostgreSQL 16** | The serving views are **small and query-heavy**: per-zone windows, per-household bills. They need point lookups by household, upserts from micro-batches (`ON CONFLICT`), **transactional replace of a day** (staging swap), and SQL for Grafana. One engine serves both speed and batch views, so the merge is a simple query. A read-only role for Grafana protects the data. | Cassandra (write scale we don't need, weaker for ad-hoc analytics and transactions); serving straight from Parquet (too slow for API latency). |
| Serving API | **FastAPI** | Typed, auto-documented (`/docs` OpenAPI) endpoints for the suggested output ("API endpoint for real-time grid load/renewable mix by zone"). Implements the **Lambda query-time merge**, and exposes Prometheus metrics and the Alertmanager webhook. | Flask (no typing or OpenAPI out of the box). |
| Dashboards | **Grafana 11** | Live-ops, billing and pipeline-health dashboards provisioned as code, reading both Postgres (business views) and Prometheus (pipeline metrics). | Superset (heavier; weaker for operational metrics). |
| Metrics & alerting | **Prometheus + Pushgateway + Alertmanager**, `prometheus_client` in every Python service | Pull-based scraping suits long-running services (simulators, Spark driver, API). The **Pushgateway** is the standard pattern for short-lived batch jobs. Alert rules are declarative and version-controlled. Alertmanager routes alerts, here to the API webhook; in production this would be Slack or PagerDuty. | Relying on Airflow/Spark UIs only (not alertable; no single view across stages). |
| Logging | **Structured JSON lines** to stdout (`common/logging_utils.py`) | Every stage logs the same shape (`ts, level, service, stage, event, …context`), so logs can be filtered with `jq` or shipped to Loki/ELK without parsing. | Free-text logs (hard to aggregate). |
| Packaging | **Docker Compose** | One command reproduces the whole platform on any laptop, with memory limits tuned for 8 GB of Docker memory. | Kubernetes (the right production target, but unnecessary to demonstrate the architecture). |

## Sizing on the demo configuration

* 250 households × 1 reading per 15 simulated minutes ≈ **80 events/s** (about 24,000 readings per simulated day).
* Total container memory limits are about 8 GB. Measured steady-state usage is lower (see the report's results section).
* The Spark batch job for one simulated day runs in local mode inside the Airflow container
  (`local[2]`). In production the same `spark-submit` would target a cluster (YARN, K8s or standalone)
  by changing `SPARK_MASTER`.
